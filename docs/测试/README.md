### 发现的 7 项工程问题

1. 团队自己的集成测试编译不过（`queueHead` 重复定义），`mvn test` 必然失败 ← **最严重**
2. 需求文档 `C-29` / `C-30` 各出现两次
3. 商品状态少一个「草稿」（需求 5 态，代码 4 态）
4. 卖家种子密码 `seller123` 改密后无法回退
5. `schema.sql` 商品 `status` 缺 CHECK 约束
6. 前端密码规则落后于后端（前端 ≥6 位，后端 ≥8 位 + 3 类）
7. 用例 `K02` 表述错误

> 另有**问题 0**（前后端手机号规则不一致）记为观察项 **OBS-014**，不计入这 7 项。

- **挑战B 新功能全部通过**：订单 5 态流转、双向取消四态边界、库存「下单占用 → 取消回补 → 完成扣减」、收藏、购物车、多件下单、转收藏、游客会话、查询台账

## 四、第四次评审（挑战C）

面向 **挑战C 版** `d34fdd9`：**挑战C 取代挑战B 的「纯线下交易、无支付、无物流、无售后」模型**，

| `测试脚本/README.md` | 运行方式、环境要求、预期结果 |
| `测试脚本/证据/` | 每条用例的完整请求与响应 |

### 这一轮测的是一条完整链路

```
下单 → 支付 → 商家确认 → 备货完成 → 发货 → 物流 4 态 → 交易完成 → 售后申请 → 受理 → 结案退款
```

**全程走真实接口，不直接改数据库造状态**——每一步都是上一个接口的结果。

### 结论

- **63 条用例，62 通过，1 失败**（9 个模块）
- **全链路一次跑通**：订单 7 态、物流 4 态（`SHIPPED → IN_TRANSIT → DELIVERING → DELIVERED`）逐跳正确
- **8 类非法操作全部正确拦截**：备货完成跳发货、重复发货、物流跳级、已签收再更新、未支付推进、未完成申请售后、已完成商家取消、越权访问
- **唯一缺陷：同一订单项可重复发起售后**（`AfterSaleService.create()` 缺"已存在未结案售后"校验），约 30 分钟可修

### 假通过审计

上一轮曾把「过程审计」写进材料，这一轮进一步**审计断言本身**：

| 类型 | 加强前 | 加强后 |
|---|---:|---:|
| 恒真断言（`True`，必定通过） | **1** | **0** |
| 宽松断言（允许多个状态码） | **3** | **0** |
| 弱断言（只比状态码，不校验内容） | **40** | **0** |

共加强 **44 处**断言。**加强后结果不变**（仍 62 通过 / 1 失败），说明原来的"通过"不是靠弱断言蒙混的。

## 五、几轮之间的关系

后三轮都不是增量迭代，而是**架构级替换**：

| 评审 | 变化 | 影响 |
|---|---|---|
| 第一轮 → 第二轮 | 挑战A：前端完全重写、新增 Java 后端、删除口令码机制 | 第一轮用例部分作废 |
| 第二轮 → 第三轮 | 挑战B：**购买模型整体替换**（意向排队 → 购物车下单） | 上一轮 114 条中 **18 条作废、15 条需改造** |
| 第三轮 → 第四轮 | 挑战C：新增支付、物流、售后三条支线，订单 5 态 → 7 态 | 用例按新链路重写，63 条全新 |

因此各轮的用例编号体系不同，**不要交叉引用**。

> 每轮都会**重跑上一轮报过的问题**，避免"修过的又回归"——
> 第三轮就是这样发现 `BUG-002`（LIKE 转义）被回归的。
