## 五、前后端一致性对照（22 条，8 条不一致）⚠️

### 5.1 客户密码：已一致 ✅

前端 `validateCustomerPassword` 已改为 **≥8 位 + 3 类**，与后端 `Validation.password()` 完全一致，6 条对照**全部一致**。

> **上一轮的问题 6 确认修复。**

### 5.2 手机号：不一致扩大了 ❌

后端放宽为「手机 / 座机 / 本地号」，但前端 `PHONE_RE` 仍是 `^1[3-9]\d{9}$`（只认 11 位手机号）。

| 输入 | 前端 | 后端 | 一致？ |
|---|:---:|:---:|:---:|
| `13800000000`、`19900000000` | 通过 | 接受 | ✅ |
| `12345`、`23800000000`、`abcdefghijk`、空 | 拒绝 | 拒绝 | ✅ |
| **`01012345678`（座机）** | 拒绝 | **接受** | ❌ |
| **`12345678`（本地 8 位）** | 拒绝 | **接受** | ❌ |
| **`1234567`（本地 7 位）** | 拒绝 | **接受** | ❌ |
| **`138-0000-0000`** | 拒绝 | **接受** | ❌ |
| **`138 0000 0000`** | 拒绝 | **接受** | ❌ |
| **`+8613800000000`** | 拒绝 | **接受** | ❌ |

**6 / 12 不一致。** 上一轮是 9 / 16 不一致，**问题没有解决，只是方向反了**：

- 上一轮：前端严（11 位）、后端松（5~20 位任意数字符号）
- 这一轮：前端仍严（11 位手机号）、后端改成了**另一套松规则**（还接受座机）

> 用户从界面进不来（前端拦住），但**直接调接口能存进座机号**。数据一致性风险仍在。

### 5.3 卖家密码：新发现的不一致 ❌

本周 7 项修复只改了**客户密码**，卖家密码的前端校验没跟着改：

```js
// frontend/src/utils/validate.js
export function validateSellerPassword(value) {
  if (password.length < 8) return '（卖家）新密码长度不能少于 8 位'   // 只查长度
  ...
}
```

但后端 `Validation.password()` 对卖家也要求 **3 类字符**。

| 新密码 | 前端 | 后端 | 一致？ |
|---|:---:|:---:|:---:|
| `abcdefgh`（8 位 1 类） | 通过 | **422 强度不足** | ❌ |
| `12345678`（8 位 1 类） | 通过 | **422 强度不足** | ❌ |
| `Ab1!ab`（6 位） | 拒绝 | 422 长度不足 | ✅ |
| `Abcd1234`（3 类） | 通过 | 200 | ✅ |

**卖家在界面上填 `abcdefgh` 不会被告知不合规，点「保存」才被后端拒绝。**

## 十、结论

1. **本周 7 项修复本身的质量是好的**：39 条修复验证**全部通过**，BUG-001、BUG-002、OBS-001 三个历史问题确认修复。
2. **客户密码的前后端一致性问题已解决**（上一轮问题 6 关闭）。
3. **回归无破坏**：84 条原有用例全部通过，说明这轮改动没有引入功能回退。
4. **但修出了两个新问题**：
   - 上传鉴权加了，**团队自己的集成测试跑挂了**（`mvn test` 仍是红的）
   - **卖家密码**的前后端规则没同步（只改了客户密码）
5. **手机号问题没有真正解决**：前端和后端各改各的，仍然不一致，用户侧不可达但接口可绕过。
