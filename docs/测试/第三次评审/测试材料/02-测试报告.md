## 一、这一轮测什么

挑战B 全面替换挑战A 的「意向 → 排队 → 先到先得 → 冻结 → 成交扣库存」模型，
改为「收藏/加购 → 从购物车选件 → 下单 → 订单 5 态 → 下单占用 / 取消回补 / 完成扣减」。

本轮**只测挑战B**：13 个功能模块，108 条用例。

| 维度 | 挑战A | 挑战B |
| --- | --- | --- |
| 购买路径 | 提交意向 → 排队 → 卖家挑队首 | **收藏/加购 → 购物车选件 → 下单** |
| 核心对象 | 购买意向（7 态） | **订单（5 态）** |
| 库存 | 成交时扣减 | **下单占用 → 取消回补 → 完成扣减** |
| 卖家操作 | 进入交易 → 标记成功/失败/作废 | **推进订单状态 / 取消订单** |
| 新增能力 | —— | **收藏、购物车、多件下单、转收藏、游客会话** |

## 五、❌ 失败项：`BUG-002` 回归

### 5.1 现象

| 用例 | 请求 | 期望 | 实际 |
| --- | --- | :---: | :---: |
| L09 | `GET /api/products?keyword=%` | 0 条 | **全部商品** |
| L10 | `GET /api/products?keyword=_` | 0 条 | **全部商品** |

### 5.2 根因

```java
// ProductService  L130~132、L404~406
where.append(" AND p.name LIKE ?");
params.add("%" + keyword.trim() + "%");     // 没有 ESCAPE，也没有转义
```

而 `Utils.likePattern()` 方法**仍然存在**，只是这里没用；上一轮的写法是：

```java
where.append(" AND p.name LIKE ? ESCAPE '\\'");
params.add(Utils.likePattern(keyword.trim()));
```

### 5.3 定性

**这是上一轮已修复的 `BUG-002` 的回归**——挑战B 重写 `ProductService` 时把转义逻辑丢了。

**严重度：高**。用户在搜索框输入一个 `%`，就会把全部商品列出来，搜索结果完全失真。

**修复建议**：恢复两行即可（`ESCAPE '\'` + `Utils.likePattern()`），约 10 分钟。

## 九、结论

1. **挑战B 的全部新功能实测通过**：订单 5 态流转、双向取消四态边界、库存「下单占用 → 取消回补 → 完成扣减」、收藏、购物车、多件下单、转收藏、游客会话、查询台账、上限分页——**106/108 通过，核心链路零失败**。
2. **前端改造干净**：27 个组件编译通过、新旧页面替换完整、状态标签与上限常量与后端一致。
3. **唯一功能缺陷是 `BUG-002` 回归**（LIKE 转义丢失），影响搜索正确性，高优先级。
4. **两个遗留红项仍未修**（卖家密码、手机号），另有 4 项迁移残留（死接口 / 死表 / 死 Service / 枚举）。

### 一个共同点

| 问题 | 是什么 |
| --- | --- |
| LIKE 转义丢了 | 重写 `ProductService` 时，旧的修复没带过来 |
| 卖家密码 | 改了客户密码，卖家密码没跟上 |
| 手机号 | 改了后端规则，前端没跟上 |

> 都是「**改了一处，配套的那处没跟上**」。建议：任何校验规则或核心逻辑变更，
> 必须同步**前端 / 后端 / 测试 / 需求文档**四处。
