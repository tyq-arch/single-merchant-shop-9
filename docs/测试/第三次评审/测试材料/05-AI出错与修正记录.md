## 一、结构性错误（影响测试结论）

### E24　挑战B 测试脚本下单入参写错，15 条用例被误判为失败

| 项 | 内容 |
| --- | --- |
| 阶段 | 首轮挑战B 冒烟 |
| 错在哪 | 下单接口 `POST /api/customer/orders` 实际要 `{"product_ids":[...]}`，脚本传了空对象 `{}` |
| 后果 | 下单返回 422，导致 O01~O22、R01~R03、S02 共 **15 条用例全部 FAIL** |
| 发现方式 | 看原始响应发现是 `VALIDATION_ERROR: product_ids 不能为空`，与「下单功能坏了」的推断矛盾 |
| 修正 | 改为 `{"product_ids":[pid]}` 后重跑，15 条全部通过 |
| 影响结论 | **是**。若不复核，会误报「挑战B 下单功能整体不可用」 |
| 是否已推翻 | 是，旧的失败结论已作废 |

> **教训**：用例失败时先看原始响应体，不要直接归因于被测系统。

### E25　加购 99 件用例设计错误

| 项 | 内容 |
| --- | --- |
| 阶段 | 首轮冒烟「缺货」用例 |
| 错在哪 | 想验证「库存不足」却往**已有 2 件**的购物车里再加 99 件，触发的是「单条购物车数量不能超过 99 件」 |
| 后果 | 得到 409，被误判为「加购超库存被拒」（实际购物车**不锁库存**，该行为是正确的） |
| 发现方式 | 读 `PreselectService.addCart` 源码，发现它只校验 `available > 0` 与单条上限，不校验库存是否够 |
| 修正 | 改用库存 3 的商品加购 5 件，实测 200（允许），下单时才返回 409 + `shortages` |
| 影响结论 | **是**。曾误以为「加购会拦库存」 |

### E26　上传鉴权用例的 multipart 格式错误，误报 401 为 422

| 项 | 内容 |
| --- | --- |
| 阶段 | 完整套件 K28 |
| 错在哪 | 手拼 multipart body 时 `boundary` 与内容不匹配（直接发了 `b"x"`） |
| 后果 | Spring 在解析阶段就返回 422，用例记为 FAIL，一度记为「上传鉴权有问题」 |
| 发现方式 | 重看请求：422 说明连控制器都没进；换正常 PNG 重测 |
| 修正 | 用正确的 multipart 重测：无 token → **401**、带 token → **200**，鉴权正常 |
| 影响结论 | **是**。已从失败清单中剔除 |

### E27　URL 查询串含中文未编码，3 条用例返回 ERR

| 项 | 内容 |
| --- | --- |
| 阶段 | 按贡献者验证（P 组） |
| 错在哪 | 直接把中文拼进查询串（`?keyword=商品A_xxx`），`urllib` 不自动编码 |
| 后果 | P31、P32、P72 三条返回 `ERR`，被记为失败 |
| 修正 | 在 `api()` 里统一 `quote(q, safe="=&%")`，重跑后三条全部通过 |
| 影响结论 | 是（短期） |

### E28　购物车残留状态导致订单金额用例误判

| 项 | 内容 |
| --- | --- |
| 阶段 | 按贡献者验证（Q 组） |
| 错在哪 | 前面的 P13 把商品数量设成 99 未复位，Q21 再加 3 件触发上限 409 |
| 后果 | Q21~Q23（订单金额 / 订单项字段 / 订单号唯一）三条 409，被误判为失败 |
| 修正 | Q 组开始前先 `DELETE /cart/{pid}` 清空，重跑全部通过 |
| 影响结论 | 是 |

> **教训**：带状态的接口测试，每个模块开始前必须显式复位。

### 四条可复用的教训

1. **用例失败先看原始响应体**，别先归因被测系统（E24、E26）。
2. **带状态接口每模块前必须复位**（E25、E28）。
3. **URL 中文必须编码**，否则会是「假失败」（E27）。
4. **端到端串起来再下结论**——接口报错不等于功能坏了，先看响应码与错误码（E24、E26）。
