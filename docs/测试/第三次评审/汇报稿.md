## 四、红项 2：卖家密码前后端不一致（70 秒）

### 4.1 现象

> "本周那 7 项修复里有一项是**密码校验**。我逐条对照了前端和后端，**客户密码确实修好了**——6 条对照全部一致。
>
> **但卖家密码没跟上。**"

| 新密码 | 前端 | 后端 | 一致 |
|---|:---:|:---:|:---:|
| `abcdefgh`（8 位 1 类） | **通过** | **422 强度不足** | ❌ |
| `12345678`（8 位 1 类） | **通过** | **422 强度不足** | ❌ |
| `Ab1!ab`（6 位） | 拒绝 | 422 长度不足 | ✅ |
| `Abcd1234`（3 类） | 通过 | 200 | ✅ |

### 4.2 根因：同一份文件里，两个函数改了其中一个

> "证据非常直接。**同一个 `validate.js`，两个函数，只改了一个**："

```js
// L42~L54  客户密码 —— 本周改过 ✅
export function validateCustomerPassword(value) {
  if (password.length < PASSWORD_MIN) { ... }
  const classes = passwordClassCount(password)      // ← 有类别判断
  if (classes < 3) return '密码强度不足：…至少 3 类（当前 N 类）'
  return ''
}

// L57~L63  卖家密码 —— 没改 ❌
export function validateSellerPassword(value) {
  if (password.length < 8) return '（卖家）新密码长度不能少于 8 位'
  if (password.length > 128) return '密码长度不能超过 128 位'
  return ''                                         // ← 完全没有类别判断
}
```

### 4.3 用户视角

> "卖家在改密页面填 `abcdefgh`，八个字母——**前端一声不响，点「保存」才被后端拒绝**。
>
> 提示还很不友好：前端什么都没说，后端突然弹一个「密码强度不足」。**用户会以为是系统坏了。**"

### 4.4 怎么修

> "把客户密码那三行判断复制到卖家密码里就行。因为后端 `Validation.password()` 对**客户和卖家是同一套规则**，前端不该分两套。"

## 五、红项 3：手机号前后端不一致（70 秒）

### 5.1 现象

> "这个最微妙——**他们把后端改宽了，但前端没动，结果不一致的方向反过来了。**"

| 输入 | 前端 | 后端 | 一致 |
|---|:---:|:---:|:---:|
| `13800000000` / `19900000000` | 通过 | 接受 | ✅ |
| `12345` / `23800000000` / `abcdefghijk` / 空 | 拒绝 | 拒绝 | ✅ |
| `01012345678`（座机） | **拒绝** | **接受** | ❌ |
| `12345678`（本地 8 位） | **拒绝** | **接受** | ❌ |
| `1234567`（本地 7 位） | **拒绝** | **接受** | ❌ |
| `138-0000-0000` | **拒绝** | **接受** | ❌ |
| `138 0000 0000` | **拒绝** | **接受** | ❌ |
| `+8613800000000` | **拒绝** | **接受** | ❌ |

> "**6 / 12 不一致。**"

### 5.2 根因：两边各改各的

```js
// 前端 validate.js  L7  —— 没动过，只认 11 位手机号
export const PHONE_RE = /^1[3-9]\d{9}$/
```

```java
// 后端 Validation.java  L18~L22  —— 本周重写成三类号码
private static final Pattern MOBILE       = Pattern.compile("^1[3-9]\\d{9}$");   // 手机号
private static final Pattern LANDLINE     = Pattern.compile("^0\\d{9,11}$");      // 座机（带区号）
private static final Pattern LOCAL_PHONE  = Pattern.compile("^\\d{7,8}$");        // 本地号
```

> "而且后端还会**先去掉空格、横线、括号**，再处理 `+86` 前缀——所以 `138-0000-0000`、`+8613800000000` 都能过。"

### 5.3 影响：用户侧不可达，但接口可绕过

> "这个问题的特点是：**正常用户撞不到，但数据会被污染。**"

| 入口 | 结果 |
|---|---|
| 从网页注册 | 被前端拦住，**进不来** |
| 直接调 `POST /api/customer/register` | **座机号、7 位本地号、带横线的号码全都能存进去** |

> "而且**上一轮是 9/16 不一致，这一轮是 6/12** —— 数字好看了，但**问题没解决，只是方向反了**：上一轮是「前端严、后端松」，这一轮还是「前端严、后端松」，只是两边的"严"和"松"都换了一套定义。"

### 5.4 怎么修

> "两条路，**必须选一条，不能各改各的**：
>
> - **A（推荐）**：前端也支持座机/本地号，两边对齐后端的宽松规则——因为需求说的是「联系电话」，不是「手机号」
> - **B**：后端收紧回只认 11 位手机号——那就要在需求里明确写「仅支持手机号」
>
> 无论选哪条，**都应该把规则写进需求文档**，避免下次又各改各的。"

> 所以我的建议不是逐条去修，而是**加一个机制**：**任何一处校验规则变更，必须同步改三个地方——前端校验、后端校验、测试用例。**"

## 八、可能被追问的问题

### Q1：39 条修复验证全过，为什么还说修得不好？

> "**修复本身是好的**，我从来没说 7 项修复有问题——BUG-001、BUG-002、OBS-001 都确认修好了。
>
> 问题是**修复的配套没跟上**：加了上传鉴权，测试没改；改了客户密码，卖家密码没改；改了后端手机号，前端没改。
>
> 所以准确说法是：**「修的没错，但没修干净。」**"

### Q2：手机号既然用户从界面进不来，为什么算问题？

> "三个理由：
>
> 一，**接口是公开的**，直接调 `POST /api/customer/register` 就能存进座机号，绕过前端；
> 二，**数据会脏**——库里同时存在 11 位手机号和 7 位本地号，后面做通知、统计都得兼容两种；
> 三，**这是需求缺失**——需求只说「联系电话必填」，没规定格式，所以前后端各自理解，才出现这个局面。"

### Q3：`mvn test` 失败，是他们的测试写得不好，还是代码有问题？

> "都不是，**是改代码的时候忘了改测试**。
>
> 测试本身写得挺好——单条用例覆盖完整业务流程。但它是**单条巨型用例**，一处挂全挂，所以上传这一处 401，整个测试就红了。
>
> 顺便说：**这也是我建议拆分用例的原因**——如果上传是独立一条，挂一条不影响其他 5 条。"

### Q4：你怎么证明这三个问题是真复现的，不是你环境问题？

> "三个都有原始证据，在 `测试脚本/证据/` 里：
>
> - `mvn test` —— 直接在 Maven 输出里，可以自己跑
> - 卖家密码 —— `r3-seller-pwd.json`，含前后端两侧结果
> - 手机号 —— `r3-fe.json`（前端函数返回值）+ `r3fix-*.json`（后端接口响应）
>
> 而且**前后端是分别测的**：前端直接 `import` 当前 `validate.js` 调函数，后端发真实 HTTP 请求。不是推测。"

### Q5：上一轮 7 个问题，还有 4 个没修，你怎么看？

> "我列一下：需求编号重复、缺草稿态、种子密码不可回退、缺 CHECK 约束。
>
> 这四个都还在。我不确定是**没排上期**还是**决定不修**——**这个要问组里**。
>
> 如果决定不修，建议在需求文档里明确写「本版不实现」，而不是留着让下一个人再报一次。"
