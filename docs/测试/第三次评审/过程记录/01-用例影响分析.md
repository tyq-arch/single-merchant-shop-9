## 一、挑战B 到底改了什么

| 维度 | 挑战A | 挑战B |
|---|---|---|
| 购买路径 | 提交购买意向 → 排队 → 卖家挑队首进入交易 | **收藏/加购 → 从购物车选件 → 下单 → 订单流转** |
| 核心对象 | 购买意向（7 态） | **订单（5 态）** |
| 库存 | 成交时扣减 | **下单占用 → 取消回补 → 完成扣减** |
| 卖家操作 | 进入交易 → 标记成功/失败/作废 | **推进订单状态 / 取消订单** |
| 新增能力 | —— | **收藏、购物车、多件下单、购物车转收藏、游客会话** |

**订单 5 态**：

```
CUSTOMER_PLACED（客户下单）
  → SELLER_CONFIRMED（商家确认）
  → STOCK_READY（备货完成）
  → SHIPPING（开始发货）
  → COMPLETED（交易完成）
                          另有 CANCELLED（已取消）
```

| 谁能取消 | 可取消状态 |
|---|---|
| 客户 | 客户下单 / 商家确认 / 备货完成（**发货前**，FR-028） |
| 商家 | 上述三个 + 开始发货（**完成前**，FR-029） |

## 五、⚠️ 发现 4 个遗留问题

### 问题 1：客户端意向入口已删，服务端意向/交易接口还在

```
CustomerController：已无任何 intents 端点  ✅ 删干净了
SellerController  ：仍有 4 个意向相关端点  ❌ 没删
  POST /api/seller/products/{id}/start-transaction
  POST /api/seller/intents/{id}/transaction
  GET  /api/seller/products/{id}/intents
  GET  /api/seller/products/{id}/intents/export
```

**影响**：形成**无法被正常触发的死接口**；持有卖家 token 仍可直接调用，攻击面没有收敛。

### 问题 2：几张表和三个 Service 全残留

```
schema.sql  ：buy_intent、queue_item、trade_record 三张表
services    ：IntentService、QueueService、TransactionService
```

**影响**：代码冗余、维护负担；数据库迁移时不敢删表。

### 问题 3：`FROZEN` 还在枚举里，但公开列表已过滤

- `Enums.ProductStatus` 仍有 `FROZEN`，而且 `VISIBLE = {ON_SALE, FROZEN}`
- 但 `bc01eaf` 又让**公开列表只返回 `ON_SALE`**

**影响**：枚举与实际行为不一致，测试时容易误判「冻结商品应该可见」。

### 问题 4：上一轮报的两个红项仍未修

| 红项 | 现状 |
|---|---|
| 卖家密码前端缺类别判断 | `validateSellerPassword` 仍只查长度 8~128 |
| 手机号前后端不一致 | `PHONE_RE` 仍只认 11 位；后端仍接受手机/座机/本地号三类 |

**影响**：红项详细用例里的 **15 条不一致，现在应该还全部存在**（需重跑确认）。
