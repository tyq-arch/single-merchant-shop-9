## 一、这个文件夹是什么

第 3 次阶段性评审的**测试岗全套材料**，本轮**只测挑战B**。

挑战B 把购买模型从「意向 → 排队 → 先到先得 → 冻结 → 成交扣库存」
整体换成「收藏/加购 → 购物车选件 → 下单 → 订单 5 态 → 下单占用 / 取消回补 / 完成扣减」。

| 目录 | 内容 | 给谁看 |
| --- | --- | --- |
| `更新汇总/` | 挑战B 改了什么（需求、后端、前端） | 组长写报告、组员同步 |
| `测试材料/` | 测了什么、怎么测的、结果如何 | 老师评审、组内复核 |
| `过程记录/` | 影响分析、中间结果、红项详细用例 | 想追细节的人 |
| `测试脚本/` `附件/` | 可重跑的脚本与证据、被引用的原始文件 | 想复核的人 |

> **汇报材料（口头汇报稿 + 汇报 PPT）仅本地保存，不发布到代码仓库。**

## 四、真实性说明（老师问「怎么证明」时看这里）

### 证据在哪

| 证据 | 位置 |
| --- | --- |
| **108 条用例的请求 + 完整响应** | `测试脚本/证据/challengeB-all-20261111-204633.json` |
| 红项 31 条前后端两侧结果 | `测试脚本/证据/r3-reditem-frontend.json`、`r3-reditem-backend.json` |

### 怎么复核（三种方式）

1. **看审计**：`测试材料/04-测试过程审计.md` 逐条列出断言强度（强 46 / 弱 56 / 静态 6），标出哪些是「仅状态码」的弱断言。
2. **看原始响应**：证据 JSON 里每条用例都带完整响应体，可逐条回看具体错误码与提示文案。
3. **自己重跑**：起后端后按 `测试脚本/README.md` 的顺序跑脚本，结果应一致。

### 为什么这些结果可信

- 每一条用例的**操作步骤由脚本发请求时自动记录**（方法 + 路径 + 请求体 + 是否带 token/guest），不是事后编的。
- 测试**从干净数据库开始**（`data` 目录重置后启动），排除历史数据干扰。
- 两个遗留红项的验证**前后端分别测**：前端直接 `import` 当前 `validate.js` 调函数，后端发真实 HTTP 请求，再逐条对照。
