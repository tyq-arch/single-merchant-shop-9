## 二、逐条详情

### E01　`eval` 取不出模块内变量

**现象**

```
ReferenceError: PHONE_RE is not defined
```

**根因**
`validate.js` 里用 `export const PHONE_RE = ...` 声明。`eval(src)` 执行后，`const` 声明的变量**只活在 eval 自己的作用域里，不会外泄**到外层。只有 `var` 和函数声明会外泄。

**修正**
改为把源码包进函数并显式返回需要的符号：

```js
const factory = new Function(src + '\nreturn { PHONE_RE, PHONE_LENGTH, validatePhone }')
const { PHONE_RE, PHONE_LENGTH, validatePhone } = factory()
```

**验证**
成功取出三个符号，16 条校验用例全部跑通。

**后续发现**：其实根本不需要这么绕——`frontend/package.json` 里有 `"type": "module"`，直接用 `.mjs` + `import` 就行（后来改成 3 行代码的脚本）。

### E02　文档里 `12345` 的提示文案写错 ⚠️ 影响了结论

**现象**
测试结果文档的"前端校验结果"表中，`12345` 这一行我写成：

> ❌ 拒绝 —— **联系电话只能输入数字**

**根因**
`12345` 是**纯数字**，不会触发"只能输入数字"这条判断。它应该是**长度不足**，提示「请输入 11 位手机号（当前 5 位）」。我填表时凭印象写错，没有逐条回填实测值。

**怎么发现的**
在写口头汇报稿、准备老师可能追问的问题时，我自查逻辑：*"12345 是数字，怎么会报'只能输入数字'？"* —— 发现矛盾，回头重跑函数验证。

**修正**
1. 重新直接调用 `validatePhone` 跑权威数据，确认 `12345` → 「请输入 11 位手机号（当前 5 位）」
2. 逐条核对 16 个号码，确认**只有这一行错**，其余 15 行与实测一致
3. 修正本地文档 + 已发布到 GitHub 的文档，提交 `af89950` 重新推送

**验证**
重新跑函数得出完整 16 条权威数据，与文档逐行比对通过。

**教训**
凡是"实测结果"，必须**从运行输出直接回填**，不能凭记忆或推断填写。

### E03　表格检查脚本误报"裸竖线"

**现象**
自写的 Markdown 检查脚本对 6 个表格的每一行都报「表格内裸竖线」。

**根因**
脚本用 `row.strip("|")` 去掉首尾竖线后，再判断"是否还含 `|`"。但单元格之间的**分隔符本身就是 `|`**，于是每一行都被误判。

**修正**
改为**按表头列数比对**：解析出每行列数，与表头列数比较，不一致才报。

**验证**
6 个表格全部列数一致，报告"无问题"——与 GitHub 实际渲染一致。

### E04　控制台 GBK 编码崩溃

**现象**

```

```

**根因**
Windows 控制台默认 GBK，脚本 `print` 了 emoji（✅）导致崩溃，且崩溃发生在已有输出之后，容易误判"脚本跑完了"。

**修正**
把所有结果**写入 UTF-8 文件**，再用读取工具看，不再依赖控制台输出。

### E06　I01 用例预期写错，产生假失败 ⚠️ 影响了结论

**现象**
边界测试第 1 轮出现 1 条 FAIL：

```
[FAIL] I01 同一客户对同一商品重复提交应被拒（FR-021）  HTTP 200
      预期：HTTP 409，实际：HTTP 200
```

**根因**
**是我的用例设计错了**，不是系统错了。I01 是客户对该商品的**第一次**提交，返回 200 完全正确；"重复提交应被拒"这件事应该由 I02（第二次提交）验证。我把两条用例的职责写反了。

**怎么发现的**

**修正**
1. I01 预期改为 200（首次提交合法）
2. I02 保持 409（重复提交被拒）
3. 重跑

**验证**
修正后 20/20 通过。

> **这一条最能说明"真实性"**：如果我看到 FAIL 就直接写进报告"发现缺陷 I01：重复提交未被拦截"，那就是**误报**。是复核响应体才避免了假缺陷。

### E08　删除重复方法的补丁多删了一个大括号

**现象**
为了验证"删掉重复的 `queueHead` 能否编译通过"，我写了补丁脚本删除第二处定义。第一次执行后：

- 再用 `git checkout` 还原文件 → 重新编译 → 回到原始失败状态（证明还原干净）

### E11　Maven 写用户目录被沙箱拒绝（连续 3 次尝试）

**现象**

```
[ERROR] java.nio.file.AccessDeniedException: C:\Users\33857\.m2\repository\org\springdoc
[ERROR] java.io.FileNotFoundException: ...\.m2\repository\org\apache\maven\plugins\resolver-status.properties (拒绝访问。)
```

**根因**
运行环境只允许写工作区内文件，而 Maven 默认把依赖下载到 `C:\Users\33857\.m2\repository`（工作区外）。

**失败过的三次尝试**

| 尝试 | 结果 |
|---|---|
| 1. 直接 `mvn compile` | 拒绝访问 `.m2\repository\org\springdoc` |
| 2. 加 `-Dmaven.repo.local=<工作区>` | 仍尝试写 `.m2\...\resolver-status.properties` |
| 3. 再加 `-Duser.home=<工作区>` | 仍然失败 |

**最终有效方案**
写一份 `settings.xml`，用 `<localRepository>` 强制指定本地仓库：

```xml
<localRepository>C:\...\_m2repo</localRepository>
```

再用 `mvn -s <settings.xml> ...` 执行 → **BUILD SUCCESS**。

> 这是**环境限制**而非项目问题。换到正常开发机不会有这个障碍。

### E14　`curl.exe -d` 传 JSON 被 PowerShell 吃掉引号

**现象**
所有 `curl.exe -d '{"k":"v"}'` 请求都返回：

```
{"error":{"code":"VALIDATION_ERROR","message":"JSON decode error","type":"json_invalid"}}
HTTP 422
```

**根因**
PowerShell 传参给原生程序时会**重写引号**，JSON 字符串的双引号被剥离，服务端收到的是非法 JSON。连纯英文内容也失败，说明与中文无关，纯粹是引号问题。

**修正**
把 JSON 写成 UTF-8 文件，用 `--data-binary "@文件"` 发送。

**验证**

```powershell
[System.IO.File]::WriteAllText("body.json", $json, [System.Text.UTF8Encoding]::new($false))
curl.exe -X POST ... --data-binary "@body.json"
```

→ **HTTP 200**，正常返回口令码。

**影响：是（已拦截）** —— 若照原样合并，手动测试步骤会指向不存在的页面，照着做必然全部失败。

**教训**
**合并前先确认每份内容是否仍然有效**，别只看文件名。

### E20　手动用例首版漏了两项

**现象**
首版手动用例 **21 条**。合并完成后才发现前端密码规则与后端不一致，补了 `M-A5` / `M-A6`，变成 **23 条**，总表 112 → 114。

**根因**
**先写手动指南、后做代码比对**——顺序反了。应该先把前后端校验规则都核一遍，再定手动用例。

**怎么发现的**
合并时顺手对照了 `utils/validate.js` 与 `Validation.java`，发现客户密码前端只要 ≥6 位、后端要 ≥8 位 + 3 类。

**修正**
补 2 条手动用例；实测后端对 `Ab1!ab`（6 位 4 类）返回 **422 密码长度不能少于 8 个字符**，确认不一致存在。

**验证**
实测复现（见报告「问题 6」）。

**影响：是（已拦截）** —— 首版漏了 2 个本应验证的点。

**教训**
**写用例前先把被测代码读全**，不要边写边发现。

### E21　手动用例脚本取不到二级类别，导致 8 条假失败

**现象**
第一次执行 23 条手动用例，8 条 FAIL，且报错五花八门：

```
M-C3  422 商品必须选择二级类别
M-D1  404 商品不存在
M-E2  404 类目不存在
M-F1  422 商品 ID 不能为空
```

**根因**
脚本要从 `GET /api/seller/categories` 里找二级类别，写成：

```python
leaf = next((c for c in cats if c.get("level") == 2), None)
```

但该接口**只返回一级类别**，二级类别嵌在 `children` 里。于是 `CAT = None`，
`M-C3` 因为没有类别被 422 拒绝，商品没建成 → 后面所有依赖该商品的用例连锁失败。

**怎么发现的**
看到 M-C3 报「商品必须选择二级类别」时觉得不对——明明传了 `category_id`。
于是单独打了一次 `/api/seller/categories`，打印返回结构，才看到二级在 `children` 里。

**修正**
改为先查顶层、再查 `children`。

**验证**
重跑 **25/25 全部通过**。

**影响：是（假失败）** —— 若不追查，会误报"多商品、库存、队列、交易全部不可用"。

**教训**
**看到同一处根因引发的连锁失败，先怀疑自己的脚本，别急着记缺陷。**

### E22　审计脚本用长度阈值判断 200，误报 2 条假通过

**现象**
第一版审计把 `B08`（客户登出）和 `K02`（卖家改密）标为「疑似假通过」，理由都是「响应体过短」。

**根因**
我用 `len(raw) < 30` 判断"是不是真实载荷"。但这两条的正常响应本来就很短：

```
B08  {"message":"已退出登录"}     19 字符
K02  {"message":"密码修改成功"}   20 字符
```

**怎么发现的**
没有直接采信审计结果，而是把这两条的原始响应调出来看——发现是合法的成功响应。

**修正**
判定改为**语义判断**：能否解析为合法 JSON 对象、是否为空、是否含 `error` 字段。

**验证**
重跑审计，两条均判定通过；全量 116 条中**已知假通过 0 条**。

**影响：是（假报警）** —— 若不核实，会向组里误报两条不存在的缺陷。

**教训**
**审计脚本自己也会误判**，它报出来的每一条都要人工看一眼原始数据。

## 四、从这些错误里提炼的方法

| 教训 | 具体做法 |
|---|---|
| 实测数据必须从输出回填 | 不凭记忆填表（E02） |
| 看到失败先看响应体，再下结论 | 避免把"自己的预期错误"误报成缺陷（E06） |
| 改代码前先备份，改完必须还原验证 | `git checkout` 后可重新编译确认回到原始状态（E08） |
| 测试要能从干净状态重跑 | 每轮清空数据库 + 唯一后缀（E07） |
| 环境限制先识别，别反复硬试 | Maven 写用户目录属沙箱限制，换方案而非重试（E11） |
| 同一错误要全局搜一遍 | E05 一个解包错误在 4 处同时存在，只改一处会再犯 |
| **主题变了，要回头检查所有相关文档** | 不能只改"主文件"；汇报稿因没跟着更新，整篇讲成了上轮内容（E16） |
| **批量替换后必须看结果** | 全局替换会误伤目录树这类结构化内容，跑完要打印出来看一眼（E17） |
| **合并 = 改文件 + 改引用 + 改数字** | 三件事必须同时做，否则会留下"21 项""112 条"这类幽灵数字（E18） |
| **合并前先确认内容是否仍有效** | 按文件名判断"都是手动指南"差点把已作废的口令码流程合进来（E19） |
| **写用例前先把被测代码读全** | 边写边发现会漏点；手动用例首版就漏了前后端密码规则不一致两项（E20） |
| **连锁失败先怀疑自己的脚本** | 同一根因导致 8 条 FAIL 时，多半是测试环境没搭对，不是系统全坏（E21） |
| **审计脚本自己也会误判** | 它报出的每一条都要调原始数据人工核对，别直接采信（E22） |
| **Windows 下 Node ESM 不能用绝对路径** | 必须用 `file:///` 或相对路径（E23） |
