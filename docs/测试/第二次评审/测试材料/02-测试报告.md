## 二、测试方法（三批通用）

### 2.1 自动化部分怎么做的

1. **取最新代码**：`git fetch && git reset --hard origin/main`
2. **编译启动**：`mvn -s <settings.xml> "-Dmaven.test.skip=true" package` → `java -jar ... --server.port=8000`
3. **探索性调用**：先用真实请求摸清每个接口的字段与响应结构（不靠猜、不靠文档）
4. **逐条发请求**：每条用例记录 时间戳 / 方法 / 路径 / 请求体 / HTTP 状态 / 完整响应体

## 六、发现的问题

### 问题 0：前后端手机号校验规则不一致（观察项 OBS-014）

- **前端**：`^1[3-9]\d{9}$`（严格 11 位）
- **后端**：`^[0-9+\-\s]{5,20}$`（5~20 位，允许 `+ - 空格`）
- **不一致**：9 / 16 个号码结论相反
- **可达性**：正常 UI 不可达（输入框限 11 位 + 失焦校验）；**直接调接口可绕过**
- **定性**：观察项（中），不判缺陷——需求只要求"电话必填"，未规定格式，前端收紧属改进
- **建议**：后端同步收紧为 11 位，并把电话格式写进需求

### 问题 1：团队自己的集成测试编译不过 ⚠️ 最严重

```
BackendIntegrationTest.java:[533,20]
已在类 com.shop.BackendIntegrationTest 中定义了方法 queueHead(java.lang.String,java.lang.String)
```

- **两处定义**：L216–220 与 L529–537，**函数体完全相同**
- **引入提交**：`fa8c4e0`（2026-10-25 23:11，Avess002）。此前是 1 处，此后变 2 处
- **后果**：`mvn test` 必然失败 → 那套 34 KB 集成测试**一条都跑不了**，团队失去自动化回归
- **根因推断**：该批提交 4 分钟内 5 条、信息全是 `Update Xxx.java`，是 **GitHub 网页编辑器**提交，没有本地编译检查
- **修复验证**：删掉 L529–537 后 `mvn test-compile` → **BUILD SUCCESS**；已 `git checkout` 还原
- **影响面**：仅测试代码，主程序不受影响（我的功能测试是独立脚本，不依赖它）

### 问题 2：需求文档 `C-29` / `C-30` 各出现两次

| 编号 | 内容 | 类型 |
|---|---|---|
| C-29 | 密码规则：≥8位+强度要求 | 改 |
| C-30 | 本期无「找回密码」功能 | 确认 |
| **C-29** | **商品状态枚举对齐为 5 态** | 改 |
| **C-30** | **「手动冻结/解冻」待确认（TBD-15）** | 待确认 |

新增条款占用了编号，原编号未顺延。**建议改为 C-31/C-32 或整体重排。**

### 问题 3：商品状态少一个「草稿」

需求状态表列 **5 态**（草稿 / 在售 / 冻结 / 售罄下架 / 手动下架），代码 `Enums.ProductStatus` 只有 **4 态**（`ON_SALE` / `FROZEN` / `SOLD_OUT` / `OFF_SHELF`）——**缺 DRAFT**。

### 问题 4：卖家种子密码 `seller123` 改密后无法回退

`seller123` 只有小写+数字 = **2 类**，不满足新强度策略。实测：改成 `Seller123!` 后想改回 `seller123`，被 **422** 拒绝。登录不受影响（登录不做强度校验），但**一旦改密就回不到初始密码**，测试环境需重置数据库。

### 问题 6：前端密码规则落后于后端

| 规则 | 前端 `utils/validate.js` | 后端 `Validation.password()` |
|---|---|---|
| 长度 | 客户 ≥6 位；卖家 ≥8 位 | ≥8 位 |
| 强度 | 无 | 大写/小写/数字/特殊字符至少 3 类 |

**实测**：`Ab1!ab`（6 位 4 类）、`abcdefgh`（8 位 1 类）前端都放行，后端均返回 **422**。
用户界面上看不出问题，点提交才被拒。**建议前端同步为 ≥8 位 + 3 类校验。**

### 问题 7：用例 `K02` 表述错误

标题写「卖家新密码与旧密码相同应被拒或允许」，但请求体是 `old_password=seller123`、`new_password=Seller123!`——**并不相同**。
这是**我写用例时的表述错误**，不影响系统结论，但会误导阅读者。已在本报告中标注。

### 问题 5：`schema.sql` 商品 `status` 缺 CHECK 约束

```sql
status TEXT NOT NULL,     -- 旧 Python 版有 CHECK (status IN (...))，Java 版没有
```

非法状态值可被直写进库（正常流程不会，但少了最后一道防线）。

## 六A、测试过程审计（自查假通过）

> 目的：核实 116 条记录是否全部真实通过，识别「断言太松导致假通过」

### 审计方法

1. 摊开每条用例的**原始响应体**（脚本落盘的 JSON），而不是只看结论列
2. 判定**断言强度**：只断言状态码 = 弱；校验了字段值 = 强
3. 对弱断言做**事后强化复验**：
   - 预期 200 → 响应必须是合法 JSON 对象、非空、不含 `error`
   - 预期 422/401/409/404 → 错误码必须是 `VALIDATION_ERROR`/`UNAUTHORIZED`/`CONFLICT`/`NOT_FOUND`
   - 预期提到 `SOLD_OUT` / `FROZEN` / `QUEUED` 等状态值 → 响应中必须真的出现

| 项 | 数量 |
|---|---:|

| 强断言（校验字段/文案） | 68 |

明细见 `04-测试过程审计.xlsx`。
